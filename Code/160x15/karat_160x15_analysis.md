# Анализ исходника Karat-3.5 / Code/160x15

Источник: https://github.com/Fmulder007/Karat-3.5/tree/main/Code/160x15  
Файл: `160x15.ino`

## Краткий вывод

Код в целом выглядит продуманным, но есть несколько потенциальных ошибок и уязвимых мест. Наиболее важные для исправления:

1. Переполнение `millis()` при проверке скорости энкодера.
2. Выход за границы OLED-экрана при отрисовке индикаторов мощности.
3. Возможное повторное срабатывание резервного копирования/восстановления.
4. Устаревший способ включения подтягивающего резистора кнопки энкодера.
5. Потенциальное переполнение в фильтре АЦП — не критично, но стоит учитывать.

## Потенциальные ошибки и уязвимости

### 1. Переполнение `millis()` при проверке скорости энкодера

В функции `readencoder()` используется условие:

`if ((actenc + minEncSpeed) >= millis()) {`

Строка около 208.

Проблема: сложение `actenc + minEncSpeed` может привести к переполнению типа `unsigned long`, особенно после длительной непрерывной работы. Это может вызвать сбой в логике определения скорости вращения.

Рекомендация: сравнивать через вычитание:

`if ((millis() - actenc) >= minEncSpeed) {`

### 2. Выход за границы экрана при отрисовке индикаторов мощности

В функции `mainscreen()` для отрисовки шкал мощности используются вызовы:

`display.rect(x00, 23, x00 + (map(fwdpower, 1, 1023, 0, 128)), 26, OLED_FILL);`  
`display.rect(x00, 28, x00 + (map(revpower, 1, 1023, 0, 128)), 31, OLED_FILL);`

Строки около 389–390.

Проблема: переменная `x00` определена как `66`. Максимальное значение `map(..., 0, 128)` равно 128. Итоговая координата X правого края прямоугольника составит `66 + 128 = 194`, что превышает стандартную ширину OLED-дисплея 128 пикселей. Это может привести к выходу за пределы видеопамяти дисплея и некорректной работе графики.

Рекомендация: ограничить ширину шкалы доступным пространством, например `128 - x00`, или пересмотреть диапазон `map()`.

### 3. Возможное повторное срабатывание резервного копирования/восстановления

В блоках `case 111` (бэкап) и `case 112` (восстановление) после достижения счётчиком значения 10 вызывается соответствующая функция:

`if (backup_index == 10) { backup(); } break;` — case 111  
`if (restore_index == 10) { restore(); } break;` — case 112

Строки около 339–343.

Проблема: после вызова `backup()` или `restore()` счётчики `backup_index` или `restore_index` не сбрасываются в 0. Если пользователь продолжит вращать энкодер в том же направлении, условие `== 10` снова станет истинным, и функция будет вызвана повторно. Это может привести к нежелательному многократному сохранению или перезаписи EEPROM.

Рекомендация: сбрасывать счётчик после выполнения операции.

### 4. Неоптимальная настройка подтягивающего резистора кнопки энкодера

Для пина кнопки энкодера используется:

`pinMode(myEncBtn, INPUT);`  
`digitalWrite(myEncBtn, HIGH);`

Строки около 140 и 145.

Проблема: формально такой подход включает внутренний подтягивающий резистор, но считается устаревшим. Более правильным и явным способом является использование:

`pinMode(myEncBtn, INPUT_PULLUP);`

Это не критическая ошибка, но улучшает читаемость и надёжность кода.

### 5. Потенциальное переполнение в фильтре АЦП — не критично

В функциях `powermeter()` и `battmeter()` используются выражения вида:

`fwdpower = (12 * fwdpower + 4 * (analogRead(fwdpin) + 1)) >> 4;`  
`rawbatt = (14 * rawbatt + 2 * (analogRead(mybattpin))) >> 4;`

Строки около 348–352.

Проблема: переменные `fwdpower` и `rawbatt` имеют тип `uint16_t`. Произведение `12 * fwdpower` или `14 * rawbatt` может переполнить 16-битный тип, если входное значение превысит примерно 5461 для коэффициента 12 или 4681 для коэффициента 14. На практике `analogRead()` возвращает значения от 0 до 1023, поэтому при нормальной работе переполнения не произойдёт. Однако при помехах или неисправности АЦП кратковременное превышение пределов может дать некорректные показания.

Рекомендация: для большей надёжности использовать 32-битные промежуточные переменные.

## Что сделано хорошо

- Активно используются `static_assert` для контроля размеров структур и смещений в EEPROM. Это отличная практика, предотвращающая повреждение данных при изменении формата.
- При расчёте КСВ в `mainscreen()` есть проверка `if (fwdpower <= revpower)`, что предотвращает деление на ноль или отрицательное значение.
- Повсеместно используется функция `constrain()` для удержания параметров в допустимых пределах.

Наиболее важными для исправления являются пункты 1 и 2, так как они могут привести к заметным сбоям в работе устройства.
